# 时长核心不变量（Invariants）

本文件记录仅靠示例用例不容易覆盖、但任意精度核心必须始终成立的数学关系。

## 1. 毫秒 ↔ Parts 必须无损

对任何合法整数毫秒 `x`：

```text
partsToMs(millisecondsToParts(x)) === x
```

该关系必须对以下情况全部成立：

- 0；
- 正数；
- 负数；
- 毫秒尾数；
- 多单位复合时长；
- 超大 BigInt。

这条不变量直接保证“按 = 得到结果后继续 + / -”不会因为把结果重新转成表达式 Parts 而改变原值。

## 2. 负复合时长的符号规则

一个 Row 内部的多个 Part 是**相加关系**。

因此负复合时长不能只给第一个 Part 加负号。

例如 `-5,400,001ms` 的规范 Parts 必须等价于：

```text
-1小时 -30分 -0.001秒
```

而不是：

```text
-1小时 +30分 +0.001秒
```

否则重新求和会改变真实时长。

Web 当前规范结构：

```json
[
  { "kind": "unit", "unit": "h", "value": "-1" },
  { "kind": "unit", "unit": "m", "value": "-30" },
  { "kind": "unit", "unit": "s", "value": "-0.001" }
]
```

该规则已加入共享跨平台 conformance fixture。

## 3. 禁止显示负零

十进制小时/分钟属于近似显示，但显示舍入后如果绝对值为 0，文本必须是：

```text
0
```

不得输出：

```text
-0
```

例如 `-1ms` 以 6 位小数显示为十进制小时：

```text
0小时
```

内部真值仍然是 `-1ms`，只是显示精度不足以表现该差值。

## 4. 规范化必须幂等

对合法 Rows：

```text
normalize(normalize(rows)) === normalize(rows)
```

避免历史迁移、Undo 恢复或跨平台序列化时，每经过一次规范化就继续改变表达式。

## 5. 性质测试

Web：`tests/duration-invariants.test.cjs`。

除了固定边界值，还使用固定 seed 的确定性大整数序列检查：

```text
milliseconds -> parts -> milliseconds
```

当前每次回归会额外检查 256 个正负超大整数值，不依赖外部 fuzz 库，也不会产生随机/flaky CI。

## 6. 跨平台要求

未来 HarmonyOS / ArkTS 不仅要通过示例 fixtures，也必须满足这些不变量。

特别是：

- 负结果继续运算必须保持原值；
- 超大负时长不能因拆分单位而改变数值；
- 显示层不得产生 `-0`；
- 内部任意精度真值不得被显示舍入反向修改。
