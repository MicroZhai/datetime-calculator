# 日期映射契约

本文件定义 Web 与未来 HarmonyOS / ArkTS 对“日期 + 时长 -> 结束日期”的共同规则。

核心原则：

> **时长是真实经过的毫秒数；日期只是把这个时长映射到设备本地日历。**

因此日期显示不能反过来改变时长真值。

## 1. 一天的含义

`1天` 永远等于：

```text
86,400,000 ms = 24小时
```

不能因为当地日历某一天恰好有 23 小时或 25 小时，就把 `1天` 改成“翻到明天同一时刻”。

## 2. 夏令时

在有夏令时的地区，本地一天可能不是 24 小时。

例如 America/New_York 2026 年春季拨快：

```text
2026-03-08 00:00 + 23小时 -> 2026-03-09 00:00
2026-03-08 00:00 + 24小时 -> 2026-03-09 01:00
```

秋季拨慢：

```text
2026-11-01 00:00 + 24小时 -> 2026-11-01 23:00
2026-11-01 00:00 + 25小时 -> 2026-11-02 00:00
```

这是正确结果，因为产品计算的是经过时长，而不是“日历加一天”。

不存在的本地时间，例如春季拨快时跳过的 `02:30`，必须判为无效日期，不能自动滚到 `03:30`。

## 3. 月底、闰年、跨年

日期映射必须由真实日历规则决定，包括：

- 1 月 31 日 + 1 天 -> 2 月 1 日；
- 2028-02-28 + 1 天 -> 2028-02-29；
- 2028-02-29 + 1 天 -> 2028-03-01；
- 2026-02-28 + 1 天 -> 2026-03-01；
- 2026-12-31 + 1 天 -> 2027-01-01；
- 负时长允许跨回前一天、上个月或上一年。

## 4. 日期起点精度

当前日期起点协议为：

```text
YYYY-MM-DDTHH:mm
```

用户第一次开启“日期”时，使用设备本地当天：

```text
YYYY-MM-DDT00:00
```

日期起点本身不保存时区偏移，属于设备本地日历语义。

## 5. 早期年份

四位及以上正年份必须保留原年份语义。

例如：

```text
0099-01-01T00:00
```

必须表示公历 0099 年，不能被 JavaScript 的旧式 Date 构造规则误解释成 1999 年。

Web 实现因此禁止直接依赖：

```text
new Date(year, ...)
```

对 0～99 年的特殊映射行为，而应显式设置完整年份。

当前产品不接受年份 0000 或负年份作为输入起点。

## 6. 超大时长

纯时长计算可以远大于 Date 可表示范围。

当：

```text
anchor + duration
```

超过平台日期范围时：

```text
时长结果仍然有效
结束日期 -> date-out-of-range
```

日期失败不得让 BigInt 时长计算失败。

## 7. 时区语义

真实产品运行使用设备当前本地时区。

因此如果用户更换系统时区，同一个无偏移日期字符串会按新的本地时区解释。这是当前产品的明确规则，不把日期起点当成全球绝对时间戳保存。

跨平台自动测试使用明确的 IANA 时区，例如：

- `UTC`
- `Asia/Shanghai`
- `America/New_York`

以验证正常日历和夏令时边界。

## 8. 共享测试

机器可读测试：

```text
tests/date-edge-vectors.json
```

Web 执行器：

```text
tests/date-edge.test.cjs
```

当前至少覆盖：

- 月底；
- 闰年 / 非闰年；
- 跨年；
- 负 1ms；
- 0099 年；
- 上海正常 24 小时日；
- 纽约春季 23 小时日；
- 纽约秋季 25 小时日；
- 夏令时不存在的本地时间。

未来 ArkTS 迁移时必须得到相同结果。
